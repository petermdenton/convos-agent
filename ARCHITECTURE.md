# Convos — engineering guide

This is the onboarding doc. Read the README first for what Convos *is*; this
explains how it actually works, why it's shaped this way, and how to change it
without breaking the parts that took weeks to get right.

## The one principle that explains everything

**The model extracts; code decides.** Every failure we've had in production
came from trusting the model with something that needed to be guaranteed:
it greeted people instead of sending the welcome, quoted prices without filing
them, claimed things were "in the doc" that weren't, resolved comment threads
it was told never to touch. Every fix has been the same move — take the
behavior away from the model and put it in code. What remains with the model
is what it's actually good at: classifying a message, extracting entities,
writing a search query, phrasing one terse reply.

Concretely, behavior lives at three tiers, and knowing which tier a rule
belongs at is most of the job:

1. **Code (deterministic, cannot fail).** Hooks, the renderer, the intake
   state machine, cron scripts. The welcome message, doc re-renders, roster
   building, comment reopening, link checking — the model can't skip these
   because they run whether or not it cooperates.
2. **Canned strings (code decides the words).** The intake ledger ("Location:
   Toronto." / "Do you know dates and how many people?") is generated by
   `trip_tasks.py intake-*` and sent verbatim. The model's only job is to
   extract `--party 4` from "4 of us" and pass it in.
3. **Prompt rules (probabilistic, strongest available for judgment calls).**
   SOUL.md + skills. React-only, file-before-you-quote, never-offer, no-👀.
   These fail maybe 5% of the time, which is why anything that *can* move
   down a tier eventually does. The ratchet: catch a violation in chat →
   phrase it as a prompt rule → if it recurs, promote it to code.

## Life of a message

A text arrives in any iMessage chat the agent is in:

1. **Photon sidecar** (Node, localhost:8789, gateway-supervised) receives it
   from iMessage and forwards to the **Hermes gateway**. Auth via a token in
   `runtime/photon-sidecar.json`. `PHOTON_REQUIRE_MENTION=false` means every
   message reaches the agent (wake-word gating happens at the behavioral
   layer, not transport). A launchd watchdog restarts the sidecar when it
   wedges (it does — `UPSTREAM_STREAM_DEGRADED`, exit 75).
2. **`agent:start` hooks fire before the model runs.**
   `collector-first-contact`: if this chat has no trip in `data/trips.db`,
   INSERT the trip (the row doubles as a dedup lock), subprocess
   `trip_doc.py create` for a real Google Doc URL, POST the single welcome
   through the sidecar. The model wakes up to a chat that already has a trip
   — its SOUL says in that case a bare greeting gets NO reply at all.
   `roster-autolink`: normalize the sender handle, look them up in macOS
   Contacts, upsert+link them to the trip's roster. This is how the
   Travelers row shows "PD, KM, LA" without anyone being asked anything.
3. **The model runs** with a fresh prompt: SOUL.md verbatim + a skills index
   (frontmatter descriptions; the model opens the full SKILL.md it needs —
   file mtimes invalidate the cache, so skill edits are live on the next
   message). For a collector chat the playbook is `group-collector`:
   classify the drop, file it via `trip_plan.py`, ✅ tapback, stay silent
   unless addressed.
4. **`agent:end` hook: `doc-sync`.** Fingerprint the trip's state (row
   counts + max rowid + max updated_at across seven tables), compare to the
   fingerprint at last render (`data/doc_sync.json`), and if anything moved,
   subprocess `trip_doc.py update`. This is the guarantee that state changes
   reach the doc even when the model forgot step 3 of its own playbook.
   No change → no API call.

## State: one SQLite file

`data/trips.db` (untracked) is the single source of truth. The interesting
tables, all owned by `scripts/`:

- `trips` — one per chat, keyed by `chat_id`. Binding is the identity: chat →
  trip → doc.
- `intake` — the three-legged-stool state machine (where / when / how-many;
  budget is deliberately not a leg and never asked). `intake_view()` returns
  the ledger text, the next question, and the locked line — the model sends
  them verbatim.
- `plan_options` — the heart. Everything anyone drops or Convos finds:
  kind (flight/stay/activity/food/transport), status lifecycle
  (option → shortlist → favorite → held → booked, or cut), price, url,
  phone, check-in/out for stays, `related_to` for attached options (the
  "🚆 Train to Game" under the ballgame), `link_ok` from the nightly link
  check. Conventions that matter: Convos's own suggestions file at default
  status (render as "Idea") — only the group promotes; booking a stay cuts
  alternatives *night-aware* (an option survives if it covers any night no
  booked stay covers).
- `plan_itinerary`, `plan_summaries` (the one-line section summaries),
  `plan_working` (the "Convos is researching…" boxes), `plan_log`
  (changelog), `travelers` + `trip_travelers` (roster, keyed by phone),
  `tasks` (the internal to-do tree — deliberately NOT rendered in the doc).

## The doc is a projection

`trip_doc.py` renders the entire Google Doc from state and replaces the whole
body via Drive `files.update` with HTML conversion (it also syncs the Drive
file *name* to the title). Never edit the doc in place; never use the Docs
API to write. If a doc ever looks mangled, `trip_doc.py update <id>` heals it
— pristine, from state.

The big consequence: **full replace orphans comment anchors.** Google hides a
margin thread once its anchored text is gone, which looks exactly like
someone silently resolved it (we burned a day on that). The doc therefore
renders a **💬 Comments & answers** section in the body, rebuilt from the
live comment threads on every update, so Q&A survives re-renders. In-thread
replies still happen — through `doc_comments.py reply` only, which prefixes
`CONVOS:` (the marker is both attribution and the watcher's "handled" bit)
and has no resolve capability at all. Resolving is for humans; a guard in the
15-minute watcher auto-reopens any thread that got resolved without a
CONVOS reply.

Freshness is rendered, not promised: un-booked prices show their quote date
after a day and an amber "recheck before booking" at 3+; the nightly link
check flags genuinely dead links (404/410/no-DNS only — bot-walls like
Hilton 403s count as alive, we learned that the hard way) and the renderer
drops dead hyperlinks, falling back to a Maps search for actives.

## Scheduled work (Hermes cron, `cron/jobs.json`)

- `trip-doc-comment-watch`, every 15m: a pre-run script (`doc_comments.py
  check`) sweeps all docs for threads needing a reply and prints a digest;
  `{"wakeAgent": false}` as the last stdout line skips the LLM entirely when
  there's nothing — the common case costs zero tokens.
- `nightly-link-check` (6:30am, no_agent) and `morning-requote` (7am, agent
  + kiwi/skiplagged/trivago) keep prices and links honest.
- One-shot `no_agent` jobs are our remote-hands pattern: deterministic
  backfills and doc refreshes run as scripts with no model involved.

## Things that will bite you

- **The cloud bridge can't delete files on the Mac** and SQLite writes over
  the mount fail. Deterministic Mac-side work goes through one-shot cron
  jobs; the bridge only reads (`mode=ro`) and copies files in.
- **Two Pythons.** The Mac's `/usr/bin/python3` is 3.9; the Google client
  needs 3.10+. `trip_doc.py` and `doc_comments.py` re-exec themselves under
  the Hermes venv interpreter — keep that shim if you touch their headers.
- **Credits are load-bearing.** Every agent run burns Nous inference
  credits. When they run out you get HTTP 402 *mid-run*: half-finished
  filings that look exactly like model flakiness. Check credits before
  debugging behavior.
- **Some noise isn't the model.** The 👀-while-processing tapback was
  hardcoded in the Photon adapter (`on_processing_start`), gated by
  `PHOTON_REACTIONS` — no prompt rule could ever stop it. If a behavior
  survives a SOUL+skill ban, go read the adapter.
- **Restart semantics differ.** Skills: live next message. SOUL: next
  prompt build. Hooks, `.env`, `config.yaml`: gateway restart. Sessions
  accumulate context — `/new` (confirmed with `/approve`) resets one chat.

## Adding a behavior (the recipe)

Say the group wants X. First ask: does X need to be *guaranteed*? If yes,
find the deterministic seam — a hook (`agent:start`/`agent:end`), the
renderer, a column + migration in `trip_plan.py`, a cron script. If it's a
judgment call, put it in `group-collector`'s SKILL.md as a hard rule with the
exact command to run, and expect ~95%. Either way: state first (schema +
CLI), renderer second (the doc follows state), prompt last. Test renders
against a scratch DB (`TRIP_TASKS_DB=/tmp/x.db trip_doc.py render`), deploy,
and let `doc-sync` propagate. Every durable rule ends up in this repo — if
it only lives in a chat message to the agent, it doesn't exist.
